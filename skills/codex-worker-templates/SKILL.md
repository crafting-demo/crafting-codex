# Codex Worker Templates

The router gives every Codex thread its own worker sandbox, built from one
template (`codex-worker` by default, generated by this repo). Any Crafting
template can serve instead, as long as it meets the one requirement the
router has: **a `codex` on PATH that is already signed in**, because the
router starts `codex app-server` on the worker and speaks to it.

Both workflows below run on the machine with this repo checked out and `cs`
logged in as a human -- worker sandboxes have neither.

## Making A Template Codex-Ready (codexify)

Copy the template (`cs template show SOURCE --def`), then make these changes
to each workspace Codex should run in. They mirror what `build-template.py`
generates for `codex-worker`, so a codexified template behaves identically.
The heavy lifting lives in the crafting-codex repo's own `sandbox-setup.sh`,
which the template checks out and runs -- the template additions are small.

1. Add a checkout of the crafting-codex repo alongside whatever the workspace
   already checks out (`CODEX_ROUTER_REPO` in `codex-cloud.conf` has the URL,
   which matters if the user runs a fork):

```yaml
    checkouts:
      - path: crafting-codex
        repo:
          git: https://github.com/crafting-demo/crafting-codex
```

2. Render the org's OpenAI key into the sandbox (skip if the org has no such
   secret; Codex then needs `codex login --device-auth` by hand):

```yaml
    system:
      files:
        - path: /home/owner/.codex-worker/openai-key
          owner: '1000:1000'
          mode: '0600'
          overwrite: true
          template: |
            {{secret "openai-api-key"}}
```

   The secret's name is `CODEX_OPENAI_SECRET` in `codex-cloud.conf`; use that
   value, not the literal above.

3. Run the worker setup on create. It installs the Codex CLI, signs it in
   from the key above, writes the approvals-off config, and lays down the
   skills and slash commands. If the workspace already has an `on_create`
   command, chain this after it with `&&`; keep the longer of the two
   timeouts, at least `10m0s`:

```yaml
    lifecycle:
      on_create:
        run:
          cmd: /home/owner/crafting-codex/sandbox-setup.sh worker
        max_retries: 2
        timeout: 10m0s
```

4. Make sure the workspace `env` puts `$HOME/.local/bin` on PATH (that is
   where the setup lands the `codex` binary):

```yaml
    env:
      - PATH=/usr/local/go/bin:/usr/local/node/bin:$HOME/.local/bin:$PATH
```

5. Add the customization the stock worker template carries, so pooled
   instances detach cleanly when claimed:

```yaml
customizations:
  - detach_env:
      enabled: true
```

Validate (`cs template validate FILE`) and create the new template. Never
edit the source template in place: teams own their templates, and the router
requirement is additive.

### Warm pool

Workers are claimed in about a second when a pool of pre-built instances
exists for the template, and built from scratch (minutes) when one does not.
Offer to create one:

```bash
cs sandbox pool create NAME-pool -t NAME --min 2 --max 6
cs sandbox pool enable NAME-pool
```

## Changing The Router's Worker Template (cr-set-template)

The template name lives in three places, and all three matter:

| Where | Read by | Survives |
|---|---|---|
| `codex-cloud.conf` (`CODEX_ROUTER_TEMPLATE`) | this repo's scripts | everything; it is the source of truth |
| `~/.codex-router/config` on the router | `lib/worker.sh` at claim time | until the router sandbox is rebuilt or restarted, which re-lays it from the router template |
| the `codex-router` template's baked copy of that config | a rebuilt router | until the template is regenerated |

So a durable change is: update `codex-cloud.conf`, edit the router's live
`~/.codex-router/config` over ssh (takes effect on the next claim, no
restart), and rebake the router template with `python3 build-template.py`
followed by `cs template update codex-router templates/codex-router.yaml`.

Do not run `./bootstrap.sh` to rebake: it also writes the *worker* template
named in the conf, and when that name is someone's own template, the version
guard protecting it from being overwritten is not guaranteed to hold.

Two settings travel with the template name:

- `CODEX_ROUTER_WORKER_WORKSPACE` must be the workspace name inside the new
  template. The router builds the worker's SSH hostname from it, so a wrong
  value makes every claim unreachable.
- `CODEX_START_DIR` is where Codex App opens threads. If the new template
  checks out a repo, this usually wants to be that checkout's path.

Existing threads keep the sandboxes they were bound to; the template only
governs new claims.
